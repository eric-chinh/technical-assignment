Project Structure

1.1 Folder Organisation

The frontend follows a feature-slice architecture. Each domain feature owns its own components, API hooks, types, and tests. Cross-feature code lives in shared/. There is no monolithic component folder.

src/ ├── app/ │ ├── router.tsx # route definitions with lazy imports │ └── store.ts # Redux store + RTK Query wiring │ ├── features/ │ ├── products/ │ │ ├── api.ts # RTK Query endpoints for products & items │ │ ├── types.ts # Product, ProductItem, ProductListItem │ │ ├── ProductListPage.tsx │ │ ├── ProductDetailPage.tsx │ │ ├── ProductForm.tsx │ │ ├── VariantsTable.tsx │ │ ├── ImageUploader.tsx │ │ └── *.test.tsx │ └── categories/ │ ├── api.ts │ ├── types.ts │ ├── CategoryListPage.tsx │ ├── CategoryForm.tsx │ ├── buildCategoryTree.ts │ └── *.test.tsx │ ├── shared/ │ ├── components/ │ │ ├── AppLayout.tsx # shell: sidebar + header + content │ │ └── ErrorBoundary.tsx # catches unhandled render errors │ ├── hooks/ │ │ └── useDebouncedValue.ts │ └── lib/ │ ├── apiBase.ts # RTK Query createApi base │ ├── axiosClient.ts # Axios instance + interceptors │ ├── errors.ts # AppError normalisation │ ├── etagStore.ts # in-memory ETag cache │ └── resolveImageUrl.ts │ ├── mocks/ │ ├── handlers.ts # MSW mock handlers (tests only) │ └── server.ts │ └── main.tsx # entry point: Provider + RouterProvider

1.2 Feature-Slice Pattern

Each feature directory is self-contained. A feature exposes only what other features need (typically its route component) — internal sub-components, hooks, and utilities stay private to the feature. This keeps coupling low and makes it straightforward to add, remove, or refactor a feature without touching unrelated code.

What lives in a feature

  • Page component(s)
  • RTK Query API slice (api.ts)
  • TypeScript interfaces (types.ts)
  • Sub-components (forms, tables)
  • Co-located unit/component tests

What lives in shared

  • App shell layout
  • Error boundary
  • Custom hooks
  • Axios instance & error utilities
  • RTK Query base configuration

3.2 State Management — Redux Toolkit + RTK Query

Redux Toolkit (RTK) is used for global state. In practice, the only global state is server data — managed entirely by RTK Query, the data-fetching and caching layer bundled with RTK. There are no hand-written Redux slices. 

// store.ts
export const store = configureStore({
  reducer: {
    [api.reducerPath]: api.reducer,   // all server state lives here
  },
  middleware: (getDefault) =>
    getDefault().concat(api.middleware),  // adds caching, invalidation, polling
});
RTK Query handles request deduplication, background refetching, cache tag invalidation, optimistic updates, and loading/error states — removing the need for any manual useEffect-based data fetching.

3.3 API Client — Axios + RTK Query custom baseQuery

Axios v1 is used as the HTTP client. Rather than using RTK Query's default fetchBaseQuery, a custom axiosBaseQuery wraps Axios so that all requests flow through the shared Axios instance (which carries interceptors for ETag capture and error normalisation). 

// axiosClient.ts — response interceptor
axios.interceptors.response.use((response) => {
  const etag = response.headers['etag'];
  if (etag) etagStore.set(response.config.url!, etag);  // cache ETag per URL
  return response;
});

// apiBase.ts — custom baseQuery fed to createApi
const axiosBaseQuery: BaseQueryFn = async ({ url, method, data, params }) => {
  try {
    const result = await axiosClient({ url, method, data, params });
    return { data: result.data };
  } catch (err) {
    return { error: toAppError(err) };   // normalise all errors to AppError
  }
};

3.4 File Uploader — Ant Design Upload + RTK Query mutation

Image upload is handled by the ImageUploader component using Ant Design's <Upload> with a custom request handler. The default upload behaviour is suppressed; instead, the component manually builds a FormData object and dispatches an RTK Query mutation.

4
API & Data Handling

4.1 Base Query & Error Normalisation

All API calls go through a single Axios instance. Errors from any endpoint are converted into a consistent AppError shape by toAppError() in errors.ts, which parses the backend's RFC-9457 ProblemDetails response body. 

interface AppError {
  status:      number;        // HTTP status code
  message:     string;        // human-readable title
  fieldErrors: FieldError[];  // [{propertyName, errorMessage}] for 400 validation
  traceId:     string | null;
  raw:         unknown;       // original response body (for non-standard shapes)
}

interface FieldError {
  propertyName: string;   // e.g. "name", "slug"
  errorMessage: string;
}

4.2 Input Validation

Validation operates on two levels: client-side (Ant Design Form rules) and server-side (FluentValidation errors mapped back to form fields).

Client-side — Ant Design Form rules

  • Name: required, max 200 characters
  • Slug: required (create only), must match /^[a-z0-9-]+$/
  • Category: required dropdown selection
  • SKU: required, max 64 characters
  • Price: required, ≥ 0
  • Qty in stock: required integer, ≥ 0

Server-side — field error mapping

When the API returns 400 Bad Request with fieldErrors, the component maps them onto Ant Design form fields so validation messages appear inline under the relevant inputs: 

// ProductForm.tsx
const fieldErrors = (err as AppError).fieldErrors ?? [];
form.setFields(
  fieldErrors.map(({ propertyName, errorMessage }) => ({
    name: propertyName.charAt(0).toLowerCase() + propertyName.slice(1),
    errors: [errorMessage],
  }))
);

4.3 Response Handling & Cache Tags

RTK Query uses a tag-based cache invalidation system. Every mutation declares which tags it invalidates, and every query declares which tags it provides.

MutationTags invalidatedEffect
createProductProductListRefetches the product list
updateProductProduct(id), ProductListRefetches the product and list
deleteProductProduct(id), ProductListRemoves from list
createProductItemProduct(productId)Refreshes detail page
deleteProductItemProduct(productId)Refreshes detail page
uploadImage / deleteImageProduct(id), ProductListUpdates image in list & detail
adjustStockProduct(productId)Refreshes stock count (after optimistic)

4.4 Concurrent Edit — ETag / If-Match

To prevent lost updates when two users edit the same product simultaneously, the app implements optimistic concurrency using HTTP ETags.

  1. GET /products/:id — the Axios response interceptor stores the ETag header in etagStore
  2. PUT /products/:id — the mutation reads the stored ETag and sends it as an If-Match header
  3. If the server responds with 409 Conflict, ProductForm shows a modal: "This product was changed by someone else" with a Reload latest button
  4. Clicking Reload invalidates the cache, fetches the fresh version, and closes the modal

Performance

5.1 Code Splitting & Lazy Loading

All three page-level components are code-split using React.lazy(). Vite automatically produces a separate JS chunk per lazy import. The browser only downloads a page's chunk when the user first navigates to that route. 

// app/router.tsx
const ProductListPage   = lazy(() => import('../features/products/ProductListPage'));
const ProductDetailPage = lazy(() => import('../features/products/ProductDetailPage'));
const CategoryListPage  = lazy(() => import('../features/categories/CategoryListPage'));

// Each is wrapped in Suspense with a loading spinner
function withSuspense(Component: ComponentType) {
  return (
    <Suspense fallback={<Spin size="large" />}>
      <Component />
    </Suspense>
  );
}

Product thumbnail images in the list use the browser's native lazy loading:

<img src={...} loading="lazy" style={{ width: 40, height: 40, objectFit: 'cover' }} />

5.2 Optimistic Updates — Stock Adjustment

The adjustStock mutation applies an optimistic update: the UI increments or decrements the stock count immediately, without waiting for the server response. If the server rejects the request (e.g. insufficient stock), RTK Query automatically rolls back the cache to its previous state. 

adjustStock: builder.mutation({
  async onQueryStarted({ productId, itemId, delta }, { dispatch, queryFulfilled }) {
    const patch = dispatch(
      productsApi.util.updateQueryData('getProduct', productId, (draft) => {
        const item = draft.items.find((i) => i.id === itemId);
        if (item) item.qtyInStock += delta;
      })
    );
    try {
      await queryFulfilled;
    } catch {
      patch.undo();   // roll back on server error
    }
  },
})

5.3 Debouncing & Prefetching

Search debounce

The product search input is debounced by 350 ms via useDebouncedValue. The API query is only fired after the user pauses typing, preventing a network request on every keystroke. 

const debouncedQ = useDebouncedValue(q, 350);
const { data } = useListProductsQuery({ q: debouncedQ || undefined, ... });

Hover prefetch

When the user hovers over a product row in the list, the detail query is prefetched silently in the background. By the time the user clicks "Edit", the data is already in the RTK Query cache — the detail page appears instantly. 

const prefetchProduct = productsApi.usePrefetch('getProduct');

// on table row hover:
onMouseEnter: () => prefetchProduct(record.id)

5.4 Error Handling Strategy

The app uses three layers of error handling, from coarse to fine:

LayerMechanismHandles
Global ErrorBoundary (class component) Uncaught render errors — shows a full-page error Result with Reload
Page RTK Query isError flag + Ant Design Result Network failure / API unreachable — inline error with Retry button
Component try/catch around mutations + message.error() Mutation failures (save, delete, stock adjust) — toast notification
Form field form.setFields(fieldErrors) Server-side 400 validation — inline messages under each input
Conflict 409 Conflict → Modal dialog Concurrent edit detection — user prompted to reload latest version
Image img onError fallback Broken image URLs — replaced with placeholder SVG
The stock endpoint returns a non-standard 409 body ({ availableQuantity } instead of ProblemDetails). The raw field on AppError preserves this original response so the component can surface a specific message: "Only N left — you requested more than that."
